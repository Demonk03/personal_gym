# Personal Gym: совместимость дизайн-handoff и бэкенда

Дата: 2026-09-13. Проверены README handoff, логика основного HTML-прототипа, app.py, training.py, db.py, metrics.py, gpt.py, SQL-схема и тесты. Это аудит контрактов и сценариев, а не визуальная приёмка или проверка развёрнутого сервиса.

**Вывод: handoff нельзя подключить к текущему API без изменений.** Внешний вид можно использовать, но формы check-in и следующего дня, жизненный цикл плана и ряд обещанных действий требуют согласования. Production-фронта ещё нет: docs/app.js — заглушка; service worker только активируется, без кеша и очереди.

P0 — блокирует корректный основной сценарий; P1 — нужен для полного соответствия handoff; P2 — уточнение отображения/контракта. Предложения ниже не являются утверждёнными изменениями правил тренировок.

| 1 | P0 · Режим check-in | Прототип: боль ≥4 — yellow, ≥8 — red; кровотечение, головокружение, слабость, сердцебиение — red. Бэк: боль ≥7 — yellow; перечисленные системные симптомы — yellow; red определяется отдельными флагами. Например боль 4 при остальных обычных ответах даёт green на бэке и yellow в макете. | **Фронт:** отображать серверные mode, reasons, blocks_workout и rule_version. Если нужны другие правила — отдельно утвердить и изменить **бэк**, а не переносить алгоритм прототипа. |
| 2 | P0 · Полнота check-in | Бэк требует leg_symptoms: trend, weakness, bilateral, saddle_numbness, bladder_bowel_change; systemic_symptoms включает fainting и severe_shortness_of_breath. В форме нет всех этих отдельных ответов. «Одышка» и «кровотечение» не определены так же точно, как серверные поля. Нельзя заполнить отсутствующие ответы false и считать их полученными. | **Фронт / дизайн:** дополнить вопросы и явное подтверждение обязательных ответов; согласовать формулировки и mapping. Бэк уже валидирует полноту и возвращает 422. |
| 3 | P0 · Облегчённый план | Прототип убирает 8 кг у моста и меняет кардио 20→12 мин. training.py уменьшает подходы, повторы и секунды через yellow_factor с округлением вниз, но сохраняет planned_weight_kg. | **Фронт:** рендерить серверный план, сравнивать с исходным снимком; убрать фиксированные пояснения «вес убран». **Бэк:** менять алгоритм только при отдельном решении о правилах. |
| 4 | P0 · «Изменить ответы» | POST prepare уже создаёт тренировку preparing. Повтор с новым ключом конфликтует с единственной активной тренировкой, со старым ключом и другим телом — с идемпотентностью. Пересчёта существующего preparing нет. | **Бэк:** атомарный пересчёт preparing с revision, повторной оценкой и обработкой перехода в red. **Фронт:** разделять черновик, preparing и in_progress. Cancel→prepare технически возможно, но создаёт лишнюю отмену в истории и не атомарно. |
| 5 | P0 · Итог тренировки | В прототипе «Нет» симптомов = none, но post-checkin принимает только better/same/worse: будет 400. Сложность в UI — 1–4, серверная шкала — 1–10; «Очень тяжело» сохранится как 4/10. | **Обе стороны:** выбрать одну семантику. Проще привести вопросы к серверным шкалам. Не преобразовывать «нет» в «лучше» без информации о состоянии до. |
| 6 | P0 · Ответ следующего дня | UI собирает сон, боль, ногу, общее состояние. API требует pain_change, leg_symptoms_change, unusual_fatigue:boolean, ready_for_similar_load:boolean. Сон не сохраняется, готовность к аналогичной нагрузке не спрашивается, leg=none не принимается. | **Фронт:** спрашивать серверные четыре показателя. Если сохраняем сон/общее состояние из дизайна — **бэк:** расширить контракт и данные для разбора; готовность нельзя выводить из «Бодро». |
| 7 | P1 · Замеры тела | Талия/грудь/бёдра/бедро есть в UI, но нет таблицы, API записи/чтения, истории, метрик и экспорта. | **Бэк:** модель измерений с датой, единицами, revision и идемпотентностью; CRUD, прогресс, экспорт. **Фронт:** форма, ограничения, пустое состояние и очередь. Альтернатива — исключить блок из первой версии. |
| 8 | P1 · Вся программа и расписание | bootstrap отдаёт только первую сессию. get_program теряет name, session_type, weekday, estimated_minutes; списка сессий нет. Подготовка принимает session_key, но фронту негде получить весь список. Нельзя достоверно построить три аккордеона, ближайшую тренировку, дни отдыха и фильтры типов. | **Бэк:** вернуть всю программу с метаданными сессий, датой начала/неделей при необходимости, расписанием и доступными session_key. Сохранять метаданные в историческом снимке. |
| 9 | P1 · Дополнительное занятие | is_extra существует в БД и метриках, но prepare его не принимает/не сохраняет. scheduled_date необязательна, а history фильтруется по ней: запись без даты исчезнет из выбранного периода. | **Бэк:** явный контракт дополнительной тренировки и её даты; корректное попадание в историю и метрики без увеличения выполнения расписания. **Фронт:** передавать выбранный тип и локальную дату. |
| 10 | P1 · «Убрать / вернуть всё» и «Пропустить» | Для пропуска в БД есть skipped/skip_reason, но API/RPC не меняют их. Удаления/восстановления плана нет. Reorder требует все ID и не заменяет удаление. | **Бэк:** операции исключения/восстановления и пропуска с revision; определить сохранение исходного плана и уже записанного факта. **Фронт:** отправлять изменения через очередь. |
| 11 | P1 · «Отменить подход» | API умеет создать и исправить подход, но не отменить/удалить. Локальное slice в прототипе не убирает факт на сервере. | **Бэк:** идемпотентная отмена подхода и корректный учёт в метриках/разборе. **Фронт:** различать ещё не отправленный, отправляемый и подтверждённый подход. |
| 12 | P1 · Замена упражнения | Разрешённые ID есть, но get_program отбрасывает reason из exercise_replacements. Ручная замена меняет exercise_id, сохраняя дозу и существующие подходы; оборудование при ручной замене не проверяется. Это может переименовать ранее выполненный факт и изменить его категорию в метриках. | **Бэк:** отдавать причины, проверять совместимость оборудования/единиц, запрещать замену после факта либо сохранять отдельные неизменяемые факты по упражнению. **Фронт:** показывать допустимые варианты из snapshot. |
| 13 | P1 · Причины автозамен и исключений | build_workout создаёт replacement_reason и omitted, но SQL prepare не сохраняет replacement_reason, а app.py не переносит omitted в запись. После GET/reload пояснения потеряны. | **Бэк:** сохранять и отдавать причины автозамены и исключённые пункты; **фронт:** строить бейджи по ним. |
| 14 | P1 · Восстановление «Сегодня» | Active API позволяет восстановить preparing/in_progress. Но нет чтения последнего заблокированного check-in: он сохраняется без workout_id. Нет готовой выдачи ожидающих next-day ответов; прототип показывает их сразу после завершения. | **Бэк:** выдача состояния дня/последней блокировки и ожидающих ответов. **Фронт:** показывать next-day по дате в timezone профиля, хранить черновики отдельно. Временный поиск через историю и детали возможен для next-day, но не для блокировки. |
| 15 | P1 · Offline и длительность | Статусы синка в прототипе — таймеры; постоянного хранения нет. API требует существующий in_progress для подходов, а start проставляет серверное now(). Если впервые запустить тренировку офлайн и позже отправить start, длительность будет неверной. | **Фронт:** IndexedDB, постоянные UUID/idempotency_key, последовательная очередь prepare→start→sets→finish и восстановление. **Решение по продукту:** новый старт только онлайн либо **бэк:** поддержать клиентское время начала с валидацией. Продолжение загруженной активной тренировки можно делать офлайн. |
| 16 | P1 · Таймаут и конфликт вкладок | API даёт статусы операций и revision_conflict. «Продолжить здесь» в прототипе лишь скрывает модалку. Повтор с новым ключом не гарантирует отсутствие дубля; revision сам по себе не блокирует вкладку, save_set не требует revision тренировки. | **Фронт:** проверить GET operations после неизвестного результата, повторять тот же запрос с тем же ключом; при 409 перечитать ресурс и согласовать очередь. Вкладки координировать локально. **Бэк:** lease нужен, только если требуется эксклюзивность между устройствами. |
| 17 | P1 · Завершение и исправление истории | API принимает completed или stopped_early от клиента, не выводя полноту. Прототип считает все пропущенные упражнения допустимым обычным завершением. «Исправить ошибочный факт» — заглушка; API исправляет подход, но не итоговый check-in. Для плашки ручной правки нет отдельного аудита. | **Обе стороны:** определить критерий завершения/пропуска и область исправления. **Фронт:** форма правки подхода с его revision. **Бэк:** audit/edited_at и правка итога, если она входит в обещание. Не выводить ручную правку из общего workout.revision. |
| 18 | P1 · Уведомления | Таблицы push_subscriptions/scheduled_jobs есть, но маршрутов подписки/настроек, отправки и worker нет; jobs.py — заглушка. В дизайне два переключателя уже активны. | **Бэк + фронт:** реализовать push и состояния разрешений; до этого переключатели disabled с честным объяснением. Согласовать время: handoff — next-day 09:00 и разбор в воскресенье; прежняя спецификация — 10:00 и понедельник 09:00. |
| 19 | P2 · Единицы и типы упражнения | API хранит кг, секунды и measurement_type; UI предлагает lb и минуты, предполагает фиксированный набор упражнений и дозу «на сторону», которой нет отдельным полем. | **Фронт:** конвертация ввода/вывода, отображение reps/seconds/weighted_reps по данным; проверка серверных диапазонов. **Бэк:** сторона/единица дозы, если нужна структурированная поддержка. Не хардкодить 5 упражнений, 8 кг или 20 мин. |
| 20 | P2 · Графики и периоды | Прототип усредняет 3 последних точки; бэк — дневные значения за 7 календарных дней. На экране одновременно периоды неделя/3 недели/месяц, а progress получает один from/to. Доли полос нагрузки не имеют знаменателя в контракте. Supabase фильтрует вес по UTC, хотя группирует по timezone профиля. | **Фронт:** использовать raw/smoothed сервера, запрашивать нужные периоды отдельно, определить шкалы полос, убрать вымышленные наблюдения. **Бэк:** локальные границы периода веса; выдача текущего веса/достаточной предыстории при необходимости. |
| 21 | P2 · Разбор недели | Формат AI структурирован и подходит для секций. Но «данные полные», номер недели и карточки фактов не приходят готовыми. noData — состояние UI; сервер может вернуть ready с текстом о нехватке данных. Генерация синхронная; нет готового фонового уведомления. | **Фронт:** факты из progress/history, AI отдельно; mapping summary/progress/setbacks/symptom_observations и предложений; текущая или предыдущая неделя явно. **Обе стороны:** определить критерий полноты, noData и период разбора. |
| 22 | P2 · Подключение и пустые состояния | health не проверяет ключ, bootstrap требует Bearer и активную программу. Прототип подменяет проверку таймером. Нет отдельного сценария отсутствующей программы, реального 401, просроченной ревизии, пустого плана после фильтрации оборудования. | **Фронт:** реальный авторизованный запрос, обработка кодов ошибок, пустого плана и отсутствующих данных. Проверить CORS разрешённого origin. Не показывать «Программа загружена» при 404. |
| 23 | P2 · Формы ответов API | В Supabase prepare возвращает workout_id/revision/status; тестовый MemoryRepository возвращает более полный bundle. operation_status возвращает сохранённый результат операции, который также не обязан быть полным bundle. | **Фронт:** после prepare и восстановления неизвестной операции при необходимости GET workouts/:id. **Бэк / тесты:** документировать фактические DTO и проверить их одинаковость между репозиториями. |
| 24 | P2 · Стек и настройки | Handoff допускает React/Vue/Svelte, прежний brief указывает vanilla HTML/CSS/JS без обязательной сборки. Переключатели темы/единиц в прототипе меняют state, но не реализуют соответствующий интерфейс. API настроек темы/единиц нет. | **Фронт:** зафиксировать стек до реализации; локальные настройки темы/единиц допустимы без изменения бэка. Если нужна синхронизация между устройствами — расширить профиль API. |

## Что уже поддержано

- Bearer-авторизация, CORS, bootstrap, серверная оценка check-in и версия правил.
- Prepare/start, чтение активной тренировки и её деталей, изменение порядка и разрешённая замена.
- Создание/исправление подходов; completed/stopped_early с итоговым check-in; cancel для preparing.
- Запись следующего дня при приведении формы к контракту.
- Вес, история, раздельные нагрузки, динамика симптомов, экспорт JSON/CSV (CSV сейчас содержит вес и подходы).
- Недельный разбор, его валидация и stale; идемпотентность и ревизии для интеграции.

## Проверка и рекомендуемый порядок

Python-тесты: 39 passed. SQL-тесты в PGlite: 7 passed (npm test). Дополнительно прямой вызов текущей оценки подтвердил: боль 4 → green; боль 8 → yellow; кровотечение → yellow; головокружение → yellow. Валидатор итогового check-in отклоняет leg_symptoms_change=none. Валидатор next-day отклоняет payload прототипа. Это проверка соответствия коду, не оценка медицинской правильности правил.

Сначала согласовать строки 1–6 и политику офлайн-старта. Затем расширить данные программы и недостающие операции, зафиксировать DTO. После этого реализовывать фронт по визуальному handoff с адаптированными формами. Замеры и push либо реализовать полностью, либо явно исключить/отключить в первом релизе. Код приложения в рамках аудита не менялся.


## Реализация после аудита

По разрешению пользователя выполнена интеграция в ветке `feat/design-integration`. Точные решения и ограничения: [контракт](api-integration.md).

- 1–6: формы приведены к серверным правилам, реализован атомарный пересчёт preparing; шкала итоговой сложности и next-day согласованы.
- 7–14: сохранение замеров, полная программа, дополнительные занятия, remove/restore/skip/undo, причины замен и выдача состояния дня реализованы.
- 15–17: новая тренировка требует сети; продолжение использует постоянную очередь. Есть восстановление операции, координация вкладок, правка подходов/итога и аудит. Пропуск означает досрочное завершение.
- 18: подписки и worker реализованы; без VAPID переключатели выключены. Рабочую доставку надо проверить после настройки окружения.
- 19–24: конвертация единиц, серверные графики, отдельные периоды, факты/покрытие недельного разбора, ошибки авторизации, кеш деталей и vanilla PWA реализованы. Настройки темы/единиц локальные.

Внешний вид сохраняет Onest, исходную палитру, карточки, тёмный экран занятия и нижнюю навигацию. Исходные файлы handoff не изменены. Проверки и граница выпуска отражены в docs/plan.md и README.md.
